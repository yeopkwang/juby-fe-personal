### A-2 방어

`src/components/NewsList.tsx:54-70`

```ts
.then((result) => {
  if (isStale) return

  /* 모양이 깨진 응답은 빈 목록이 아니라 실패다. 뭉개면 실패가 조용해진다 */
  if (result === null || !Array.isArray(result.newsList)) {
    throw new UserFacingError('뉴스를 불러오지 못했습니다.')
  }

  // setState 콜백 안의 예외는 아래 catch로 안 온다. 응답은 밖에서 꺼내 둔다
  const received = result.newsList
  // 첫 장은 갈아끼우고, '더 보기'로 받은 장은 뒤에 잇는다
  setItems((previous) =>
    page === 0 ? received : [...previous, ...received],
  )
  setTotalCount(result.totalCount)
})
```

두 가지를 했다.

1. **응답 필드를 업데이터 밖에서 꺼낸다.** 이게 메커니즘에 대한 수정이다. 안에서 파면 예외가 렌더 단계로 새고, 밖에서 꺼내면 프라미스 안에서 나 `.catch()`가 받는다.
2. **깨진 응답을 빈 목록이 아니라 실패로 보낸다.** 빈 배열로 폴백하면 실패가 조용해져 `RG-4`와 같은 성격이 된다. 화면에 이미 두 자리가 따로 있었다 — 실패는 `LoadFailure`, 빈 목록은 "관련 뉴스를 찾지 못했습니다."

### A-3 ErrorBoundary 범위

`ErrorBoundary`에 `fallback` prop을 더하고(`src/components/ErrorBoundary.tsx`), 뉴스 영역만 감쌌다.

```tsx
{/* 뉴스가 그리다 터져도 이 칸만 비운다. 차트·시세까지 함께 사라지면 안 된다 */}
<ErrorBoundary
  resetKey={stockCode}
  fallback={<LoadFailure message="뉴스를 불러오지 못했습니다." />}
>
  <NewsList key={stockCode} stockCode={stockCode} />
</ErrorBoundary>
```

폴백은 지시대로 `LoadFailure`를 쓴다. `onRetry`를 안 넘겨 버튼은 안 그린다 — 렌더가 터진 상태는 그대로 다시 그려도 같은 데이터로 같은 곳에서 터진다.

`resetKey={stockCode}`라 종목을 옮기면 저절로 펴진다.

## 작업 B — AiPage의 닿을 수 없는 '다시 시도'

### B-1 수정 — **두 곳 모두**

**`ai.ts:65` 문구 첫 렌더 결과 (캡처 `b-2-ok.png`):** 두 문단이 빈 줄을 두고 정상적으로 나뉜다. 오탈자·줄바꿈·레이아웃 문제 **없음**.

### B-2를 어떻게 태웠는가 — 방법을 밝혀 둔다

②③④는 **응답 주입으로 태울 수 없다.** `/api/open-ai`가 허용 목록에 없어 `client.ts`가 fetch에 닿기 전에 `BlockedPathError`를 던지므로, `page.route()`가 볼 요청 자체가 없다.

허용 목록을 잠시 여는 방법을 시도했으나 **정책상 차단됐다.** 우회하지 않았다.

대신 **유일한 통신 창구인 `client.ts` 모듈만 테스트용으로 바꿔 끼웠다**(Playwright `page.route`로 `/src/api/client.ts` 응답을 교체). `ai.ts`와 `AiPage`는 저장소의 진짜 코드가 그대로 돈다. 소스 파일은 건드리지 않았다.

### B-3 기록만 (수정 금지 — 지시대로 손대지 않음)

`ask()`가 `get<null>()`로 **보내기만 하고 응답 객체는 프론트가 조립한다** — `sessionId`는 로컬 카운터, `answer`는 하드코딩 문구.

`AiPage.tsx:101`·`115`의 함수형 업데이터가 `result.answer`·`result.sessionId`를 파는데도 안전한 건 **방어가 있어서가 아니라 그 값들이 널이 될 수 없어서**다.

> 📮 **백엔드가 요청 ⑫를 처리해 진짜 응답이 오기 시작하면, 그 조립을 걷어내는 순간 두 자리가 정확히 NewsList와 같은 구조가 된다.** 그때 A-2와 같은 방어(응답 필드를 업데이터 밖에서 꺼내기)를 함께 넣어야 한다.

## 측정 문제로 판명된 것

**있음 — 한 건. 하마터면 잘못된 결과를 보고할 뻔했다.**

B-2 ②③을 처음 돌렸을 때 문구가 전부 fallback("불러오지 못했습니다. 잠시 후 다시 시도해 주세요.")으로 나왔다. 코드가 틀린 게 아니라 **내 stub 탓**이었다.

```
진짜 client.ts :  from "/src/utils/error.ts?t=1787533096870"
내 stub        :  from "/src/utils/error.ts"          ← 쿼리 없음
```

Vite가 모듈 URL에 `?t=`를 붙이는데 stub이 그걸 안 붙여 **`error.ts`가 두 벌 로드**됐다. 클래스가 달라지니 `instanceof`가 전부 false가 되고 `toUserMessage`가 fallback으로 샜다.

**중간에 넣은 확인용 probe도 같은 이유로 잘못된 답을 줬다** — probe 자신도 쿼리 없이 import해서, stub 인스턴스끼리 비교하며 "같은 클래스"라고 답했다. 화면 텍스트를 안 보고 그 probe만 믿었으면 그대로 넘어갔다.

실행 중에 진짜 URL을 읽어 맞춘 뒤 네 줄 모두 기대대로 나왔다.

§6이 "지금 보고 있는 게 코드 문제인가 측정 문제인가를 한 번 물어라"라고 한 게 이 경우다.
